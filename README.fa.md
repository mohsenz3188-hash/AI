# نوا — پروژهٔ هوش مصنوعی قابل نصب روی سرور

نوا یک فضای کار تحت وب با رابط فارسی و راست‌به‌چپ است. برنامه روی سرور شما اجرا می‌شود و از طریق API به مدل‌های هوش مصنوعی وصل می‌شود. مدل آماده داخل این بسته نیست؛ کلید معتبر و اعتبار سرویس مدل لازم است. برای متن می‌توانید سرویس محلی سازگار نیز معرفی کنید.

## امکانات موجود

- گفتگوی جریانی؛ نمایش پاسخ هم‌زمان با تولید.
- نوشتن کد، توضیح، بازبینی و رفع خطا در زبان‌هایی که مدل انتخابی می‌شناسد؛ کد قابل کپی است.
- انتخاب آزاد زبان پاسخ، ترجمه و خلاصه‌سازی؛ انتخاب زبان محدود به فهرست نمونه نیست.
- پیوست حداکثر سه فایل متنی یا کد UTF-8؛ هر فایل حداکثر ۲۰ هزار نویسه و مجموع درخواست حداکثر ۴۰ هزار نویسه.
- تاریخچهٔ دائمی گفتگو، جستجوی عنوان، تغییر نام، حذف و خروجی Markdown.
- تولید تصویر با توضیح، نسبت تصویر مربع/افقی/عمودی، گالری خصوصی، دانلود و حذف.
- حساب مدیر، رمز هش‌شده با scrypt، نشست HttpOnly، کنترل Origin، محدودیت درخواست و محافظت از تصاویر.
- رابط واکنش‌گرا برای گوشی و دسکتاپ؛ بدون اسکریپت یا فونت شخص ثالث در مرورگر.
- Docker Compose، Caddy، HTTPS خودکار برای دامنه، دادهٔ ماندگار و اسکریپت پشتیبان‌گیری.
- نصب از مخزن خصوصی گیت‌هاب، نصب‌کنندهٔ Debian/Ubuntu و بررسی خودکار GitHub Actions.

هیچ مدلی تضمین نمی‌کند همهٔ زبان‌های طبیعی و برنامه‌نویسی را با کیفیت یکسان بفهمد. نوا انتخاب زبان را محدود نمی‌کند، ولی دقت به مدل بستگی دارد. اجرا و کامپایل کد، دسترسی به ترمینال، جستجوی وب، PDF/Word، ورودی تصویری و صوتی در این نسخه وجود ندارد. فایل‌ها به‌عنوان متن تحلیل می‌شوند. این نسخه یک حساب مالک دارد؛ برای سرویس عمومی چندکاربره نیاز به توسعهٔ کاربران، سهمیه‌بندی و پرداخت دارید.

## پیش‌نیاز سرور

Ubuntu 22.04/24.04 یا Debian 12/13، دسترسی root یا sudo، Git، پیشنهاد حداقل ۲ هسته، ۲ گیگابایت RAM و ۱۰ گیگابایت فضای آزاد. برای استفاده از API به GPU نیاز ندارید. مدل محلی سخت‌افزار جداگانه متناسب با اندازهٔ مدل می‌خواهد.

ارتباط خروجی به سرویس مدل و مخازن بسته‌ها باید برقرار باشد. پورت‌های TCP 80 و 443 باید در فایروال سیستم و پنل ارائه‌دهنده باز باشند. اگر وب‌سرور دیگری این پورت‌ها را اشغال کرده، ابتدا تنظیمات آن را با Caddy هماهنگ کنید. نصب‌کننده فایروال یا وب‌سرور موجود را خودسرانه تغییر نمی‌دهد.

## آپلود در گیت‌هاب خصوصی

۱. مخزن تازه‌ای با نام دلخواه، مثلاً `nava-ai`، و دسترسی Private بسازید.

۲. **محتویات پوشهٔ پروژه** را در ریشهٔ مخزن قرار دهید؛ `install.sh` و `compose.yaml` باید در ریشه باشند. پوشه‌های مخفی `.github` و فایل‌های `.gitignore` و `.dockerignore` هم منتقل شوند. می‌توانید از GitHub Desktop یا فرمان‌های زیر استفاده کنید:

```bash
git init -b main
git add .
git commit -m "Add Nava AI"
git remote add origin https://github.com/YOUR_USER/nava-ai.git
git push -u origin main
```

پیش از commit، `.env` یا فایل‌های واقعی کلید را اضافه نکنید. `.env.example` فقط الگوی تنظیمات است. مخزن خصوصی دسترسی را به افراد مجاز محدود می‌کند؛ کلید سرویس همچنان در تنظیمات سرور نگهداری می‌شود.

## نصب تک‌خطی از مخزن خصوصی

پس از آپلود، `YOUR_USER/nava-ai` را با نام واقعی مالک و مخزن عوض کنید و در سرور اجرا کنید:

```bash
git -c credential.helper= clone https://github.com/YOUR_USER/nava-ai.git && cd nava-ai && sudo bash install.sh
```

این خط به Git نصب‌شده نیاز دارد. اگر نیست: `sudo apt-get update && sudo apt-get install -y git`.

در درخواست Git، نام کاربری گیت‌هاب و به‌جای رمز، **توکن گیت‌هاب** وارد کنید. توکن هنگام تایپ نمایش داده نمی‌شود. برای نصب، Fine-grained token را فقط به همین مخزن و دسترسی Contents: Read محدود کنید؛ ممکن است سازمان نیاز به تأیید دسترسی داشته باشد. برای آپلود از رایانهٔ خود، حساب یا توکن شما به اجازهٔ نوشتن هم نیاز دارد. توکن را در URL نگذارید. دستور بالا credential helper را برای clone غیرفعال می‌کند تا خودش توکن را ذخیره نکند.

اگر کلید SSH مجاز قبلاً روی سرور تنظیم شده، این نسخه هم قابل استفاده است:

```bash
git clone git@github.com:YOUR_USER/nava-ai.git && cd nava-ai && sudo bash install.sh
```

لینک `raw.githubusercontent.com` بدون احراز هویت، نصب از مخزن خصوصی را انجام نمی‌دهد. توکن واقعی در فرمان تک‌خطی قرار نگرفته است.

### راه جایگزین با ورودی مخفی توکن

اگر فایل‌های ZIP را روی سرور دارید، اسکریپت زیر توکن را با ورودی مخفی می‌گیرد، مخزن را دریافت می‌کند و نصب‌کننده را اجرا می‌کند:

```bash
bash scripts/github-install.sh YOUR_USER/nava-ai main
```

اسکریپت از `GITHUB_TOKEN` صادرشده در محیط هم پشتیبانی می‌کند. مقدار واقعی آن در سورس نیست؛ فایل `.env.example` محل نام این متغیر را مشخص کرده است. از قراردادن مقدار توکن در history ترمینال خودداری کنید. این متغیر برای دریافت سورس است و به سرویس وب ارسال نمی‌شود.

### نصب‌کننده چه می‌پرسد؟

- IP یا دامنه؛ بدون پورت و مسیر.
- نام کاربری و رمز مدیر با حداقل ۱۲ نویسه.
- کلید API متن، آدرس API و مدل‌های مجاز.
- کلید و آدرس سرویس تصویر و مدل تصویر؛ کلید خالی تصویر از کلید متن استفاده می‌کند.

برنامه در `/opt/nava-ai` قرار می‌گیرد و کلیدها در `.env` با دسترسی فایل محدود ذخیره می‌شوند. ورودی خالی کلیدها امکان نصب را می‌دهد، ولی قابلیت مربوط تا زمان تنظیم کلید فعال نمی‌شود. هیچ کلید واقعی همراه بسته وجود ندارد.

## IP و دامنه

**IP:** هنگام نصب IP سرور را وارد کنید. برنامه در `http://SERVER_IP` در دسترس قرار می‌گیرد. این حالت HTTP است و ارتباط را رمزگذاری نمی‌کند؛ برای ورود و استفادهٔ روزمره، دامنهٔ HTTPS مناسب است.

**دامنه:** رکورد A زیردامنه، مثلاً `ai.example.com`، را به IPv4 سرور وصل کنید. رکورد AAAA را فقط وقتی تنظیم کنید که IPv6 سرور درست کار می‌کند. هنگام نصب همان دامنه را وارد کنید. Caddy با دسترسی صحیح DNS و پورت‌های 80 و 443 گواهی صادر و HTTP را به HTTPS هدایت می‌کند. بدون DNS صحیح صدور گواهی موفق نمی‌شود.

برای تبدیل نصب IP به دامنه، در `.env` این سه مقدار را تنظیم کنید و سرویس‌ها را دوباره بسازید:

```dotenv
SITE_ADDRESS=ai.example.com
APP_ORIGINS=https://ai.example.com
COOKIE_SECURE=true
```

```bash
cd /opt/nava-ai
sudo docker compose up -d --force-recreate
```

این بسته هر دو حالت IP و دامنه را پشتیبانی می‌کند. در حالت دامنه، نشانی اصلی دامنه است؛ برای نمایش هم‌زمان چند نشانی، Caddyfile و APP_ORIGINS را متناسب تنظیم کنید. ترکیب کوکی امن دامنه با ورود HTTP روی IP نیازمند تنظیم جداگانه است. مقدار wildcard برای APP_ORIGINS مجاز نیست.

## کلیدها، مدل‌ها و هزینه

نمونهٔ پیش‌فرض متن: `gpt-4.1-mini,gpt-4.1`. نمونهٔ تصویر: `gpt-image-1`. در دسترس بودن این مدل‌ها به حساب و سرویس شما بستگی دارد؛ مدل‌های مجاز حساب خود را تنظیم کنید. اشتراک رابط ChatGPT جای اعتبار API را نمی‌گیرد.

| متغیر | کاربرد |
| --- | --- |
| OPENAI_API_KEY | کلید سرویس متن؛ فقط سمت سرور |
| OPENAI_BASE_URL | آدرس API متن تا `/v1` |
| CHAT_MODELS | مدل‌های قابل انتخاب، جداشده با ویرگول |
| IMAGE_API_KEY | کلید جداگانهٔ تصویر؛ خالی یعنی استفاده از کلید متن |
| IMAGE_BASE_URL | آدرس API تصویر؛ مستقل از API متن |
| IMAGE_MODEL | مدل تولید تصویر |
| MAX_OUTPUT_TOKENS | سقف طول پاسخ متن |
| GITHUB_TOKEN | فقط ابزار اختیاری دریافت مخزن؛ به کانتینر برنامه داده نمی‌شود |

متن از `/chat/completions` با `stream=true` و `max_tokens` استفاده می‌کند. سرویس سازگار باید پیام‌های system/user/assistant و خروجی SSE استاندارد را پشتیبانی کند. مدل‌هایی که فقط Responses API یا پارامترهای متفاوت می‌پذیرند، به تغییر adapter نیاز دارند.

تصویر از `/images/generations` استفاده می‌کند و خروجی `data[0].b64_json` در قالب PNG/JPEG/WebP لازم است. خروجی فقط URL در این نسخه پشتیبانی نمی‌شود. اندازه‌ها باید با مدل تصویر سازگار باشند. بعضی مدل‌های تصویر به تأیید حساب ارائه‌دهنده نیاز دارند.

کلیدها وارد مرورگر نمی‌شوند، ولی پیام‌ها و فایل‌های ارسالی شما برای پردازش به سرویس انتخابی فرستاده می‌شوند. خصوصی‌بودن مخزن به معنی اجرای محلی مدل نیست. مصرف API هزینه دارد؛ سقف بودجه را در حساب ارائه‌دهنده هم تنظیم کنید.

محدودیت داخلی این نسخه: حداکثر دو گفتگوی در حال تولید، یک تصویر هم‌زمان، ۶۰ درخواست متن و ۱۰ تصویر در ساعت برای حساب مدیر. این محدودیت‌ها با راه‌اندازی مجدد برنامه بازنشانی می‌شوند. تاریخچه و تصاویر روی دیسک باقی می‌مانند؛ برای جلوگیری از پرشدن دیسک، فایل‌های غیرضروری را از رابط حذف کنید. فهرست رابط آخرین ۲۰۰ گفتگو و ۱۰۰ تصویر را نمایش می‌دهد. حافظهٔ ورودی مدل حداکثر ۶۰ هزار نویسه از پیام‌های اخیر است، نه کل تاریخچهٔ نامحدود.

## مدل متن محلی

برای مثال Ollama یا vLLM با endpoint سازگار با Chat Completions قابل اتصال است. آدرس باید از داخل کانتینر app قابل دسترسی باشد؛ `localhost` داخل کانتینر، میزبان VPS نیست. در صورت اجرای Ollama روی همان میزبان، دسترسی شبکهٔ خصوصی مناسب و نگاشت host-gateway را خودتان تنظیم کنید. endpoint مدل را بدون محافظت روی اینترنت عمومی باز نکنید.

```dotenv
OPENAI_BASE_URL=http://YOUR_PRIVATE_MODEL_HOST:11434/v1
OPENAI_API_KEY=local-placeholder
CHAT_MODELS=YOUR_INSTALLED_MODEL
```

Ollama معمولاً کلید را بررسی نمی‌کند، اما برنامه برای تشخیص تنظیم‌شدن سرویس مقدار غیرخالی می‌خواهد. سرویس تصویر همچنان جداگانه تنظیم می‌شود؛ برای استفادهٔ کاملاً محلی باید سرویس تصویر سازگار هم داشته باشید.

## اجرای دستی و توسعه

اگر Docker و Compose از قبل آماده‌اند:

```bash
python3 scripts/configure.py .env
docker compose up -d --build --wait
```

برای توسعه بدون Docker، Python 3.12 لازم است:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python scripts/configure.py .env
export APP_ORIGINS=http://localhost:8000,http://127.0.0.1:8000
export COOKIE_SECURE=false
uvicorn app.main:app --env-file .env --host 127.0.0.1 --port 8000
```

گزینهٔ env-file تنظیمات را می‌خواند و آن‌ها را به‌عنوان فرمان shell اجرا نمی‌کند. متغیرهای صادرشده در محیط بر فایل اولویت دارند.

یک worker استفاده کنید؛ کنترل هم‌زمانی و محدودیت‌ها در حافظهٔ همان پردازش هستند. سرویس app در Compose پورت عمومی ندارد و فقط Caddy به آن وصل می‌شود؛ تنظیم اعتماد به proxy در Dockerfile بر همین اساس است. هنگام تغییر توپولوژی شبکه، محدودهٔ اعتماد proxy را نیز تغییر دهید.

## به‌روزرسانی و عیب‌یابی

در پوشهٔ clone اولیه:

```bash
git pull --ff-only
sudo bash install.sh
```

تنظیمات نصب قبلی و volume داده‌ها حفظ می‌شود. تغییر مدل یا کلید در `/opt/nava-ai/.env` با `sudo docker compose up -d --force-recreate` اعمال می‌شود. رمز را به‌صورت متن ساده در ADMIN_PASSWORD_HASH ننویسید؛ از تابع hash_password در `app/security.py` استفاده کنید. هنگام تغییر رمز، نشست‌های موجود تا پایان اعتبارشان فعال‌اند؛ برای ابطال فوری، جدول sessions را از دیتابیس پاک کنید.

```bash
cd /opt/nava-ai
sudo docker compose ps
sudo docker compose logs --tail=100 app caddy
```

خطای دسترسی مدل: کلید، اعتبار، نام مدل و مجوز حساب را بررسی کنید. خطای Origin: پروتکل و دامنهٔ مرورگر باید دقیقاً در APP_ORIGINS باشند. مشکل HTTPS: DNS، پورت‌ها، رکورد AAAA و گزارش Caddy را بررسی کنید. `/healthz` سلامت برنامه و دیتابیس را نشان می‌دهد، نه موجودی حساب مدل یا صدور گواهی دامنه.

## پشتیبان‌گیری و بازیابی

```bash
cd /opt/nava-ai
sudo bash scripts/backup.sh
```

اسکریپت هنگام snapshot، برنامه را موقتاً متوقف و سپس دوباره راه‌اندازی می‌کند. دیتابیس، نشست‌ها و تصاویر در فایل فشرده ذخیره می‌شوند. `.env` داخل پشتیبان نیست؛ جداگانه و امن نگهداری کنید. Caddy گواهی‌ها را در volume جداگانه نگه می‌دارد و در صورت نیاز می‌تواند دوباره صادر کند.

برای بازیابی، سرویس app را متوقف کنید و فایل پشتیبانِ مورداعتماد را در volume دادهٔ همان نصب استخراج کنید. این کار داده‌های هم‌نام را جایگزین می‌کند؛ قبلش snapshot تازه بگیرید. نام پیش‌فرض volume برابر `nava-ai_app_data` است:

```bash
sudo docker compose stop app
sudo docker run --rm -v nava-ai_app_data:/data -v "$PWD/backups:/backup:ro" --entrypoint sh nava-ai-app -c 'tar xzf /backup/YOUR_BACKUP.tar.gz -C / --no-same-owner'
sudo docker compose start app
```

کانتینر بازیابی با همان کاربر برنامه فایل‌ها را می‌نویسد. فایل پشتیبان فقط داده است و شامل توکن‌های نشست حساس می‌شود؛ آن را عمومی نکنید. دستور `docker compose down` داده را حفظ می‌کند؛ گزینهٔ `-v` داده‌های volume را حذف می‌کند.

## ساختار و آزمون

`app/main.py`: API، احراز هویت، گفتگو و تصاویر. `app/provider.py`: اتصال مدل. `app/static`: رابط. `scripts`: تنظیمات، دریافت مخزن و پشتیبان‌گیری. `tests`: آزمون‌های کاربردی.

```bash
python -m unittest discover -s tests -v
node --check app/static/app.js
bash -n install.sh scripts/github-install.sh scripts/backup.sh
```

آزمون‌ها از پاسخ‌های کنترل‌شده استفاده می‌کنند و هزینهٔ API ندارند. آزمایش واقعی تولید تصویر و متن به کلید شما نیاز دارد. استقرار روی VPS، DNS و HTTPS واقعی باید پس از واردکردن اطلاعات همان سرور انجام شود.
